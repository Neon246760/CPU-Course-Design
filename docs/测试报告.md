## 2. 测试目的

本次测试不是为了演示一个可交互的最终应用，而是确认以下完整链路能够在真实硬件上工作：

1. Vivado 能针对实板上的 XC7A100T 正确完成综合、实现和 bitstream 生成；
2. bitstream 能通过 JTAG 配置 FPGA；
3. 100 MHz 板载时钟能够产生稳定的 25 MHz CPU 时钟，复位能够正确释放；
4. CPU 能从片内指令 BRAM 取出并执行 `bringup` 程序；
5. CPU 能完成基本运算、数据相关处理、片内数据 BRAM 读写和条件分支；
6. CPU 的访存总线能够访问 GPIO、UART、LCD 和 `TOHOST` 等 MMIO 寄存器；
7. UART、LED 和 LCD 三条相互独立的观察通道能够给出一致结果；
8. 按键、拨码开关、板级输入同步和调试 LED 复用逻辑能够工作。

测试链路可以概括为：

```text
JTAG 下载 bitstream
        |
        v
FPGA 完成配置 ----> MMCM 锁定 ----> 25 MHz CPU 时钟与同步复位
                                      |
                                      v
                              IMEM 中的 bringup 程序
                                      |
             +------------------------+------------------------+
             |                        |                        |
             v                        v                        v
       DMEM 读写/比较          GPIO -> 板载 LED        MMIO 总线握手
                                                               |
                                                +--------------+-------------+
                                                |                            |
                                                v                            v
                                         UART -> CP2102               LCD -> ST7571
                                                |                            |
                                                v                            v
                                          BOOT / PASS                  测试条纹
```

只有上述链路依次成立，程序才会在最后写入 `TOHOST=1`，点亮全部 LED 并输出 `PASS`。

## 3. 当前硬件配置的含义

板级顶层当前采用保守配置：

- 指令存储器 IMEM：2048 × 32 bit，即 8 KiB；
- 数据存储器 DMEM：2048 × 32 bit，即 8 KiB；
- I-Cache：关闭；
- D-Cache：关闭；
- 动态分支预测：关闭；
- UART：仅实现发送，115200 baud、8N1、无流控；
- LCD：硬件状态机负责复位、初始化、清屏及 SPI 发送；
- `PB0`：作为外部中断输入；
- `SW7`：选择普通 LED 模式或调试 LED 模式。

关闭 Cache 和动态分支预测的目的是先验证 CPU、BRAM 和外设的最短闭环，减少首次下板时的故障定位范围。因此，本次通过不代表 Cache 和分支预测器已经通过实板验证。

## 4. 启动程序的实际执行过程

### 4.1 阶段一：CPU 启动

程序首先执行：

```asm
lui   x10, 0x20000
addi  x1, x0, 1
sw    x1, 0(x10)
```

这三条指令把 `1` 写到地址 `0x2000_0000` 的 GPIO 输出寄存器，因此 LED0 点亮。

随后，程序依次把 `B`、`O`、`O`、`T` 和换行符写入 UART TXDATA 寄存器 `0x2000_0010`，串口显示：

```text
BOOT
```

### 4.2 阶段二：ALU、相关处理和数据 BRAM 自检

程序完成以下计算：

```text
x2 = 5
x3 = 7
x4 = x2 + x3 = 12
DMEM[0] = x4
x5 = DMEM[0]
比较 x5 与 x4
```

如果读回值与计算值相同，程序向 GPIO 写入 `0x0F`，使 LED0～LED3 点亮；如果不同，则进入失败循环并输出 LED 图案 `0x55`。

这段很短的程序实际同时覆盖了几种关键情况：

- `ADD` 的算术结果正确；
- `SW` 能把数据写入片内数据 BRAM；
- `LW` 能从同一地址读回数据；
- `ADD` 后紧跟使用其结果的 `SW`，验证 store-data 数据相关能够被正确处理；
- `LW` 后紧跟读取加载结果的 `BNE`，验证 load-use 停顿或前递处理；
- `BNE` 能根据相等比较选择不跳转；
- 数据地址 `0x1000_0000` 能被地址译码器正确选中为 DMEM，而不是误选为 MMIO。

因此，LED0～LED3 点亮的含义不只是“加法结果为 12”，而是 CPU 流水线、数据相关控制、数据存储器和分支判断共同完成了一次端到端检查。

### 4.3 阶段三：等待 LCD 初始化

程序循环读取 LCD 状态寄存器 `0x2000_0028`：

```asm
lw    x12, 40(x10)
andi  x12, x12, 2
beq   x12, x0, wait_lcd
```

在 LCD 初始化完成前，`BEQ` 会反复跳回；完成后退出循环。这一阶段验证：

- MMIO 状态寄存器可以被 CPU 读取；
- `LW -> ANDI` 的相邻数据相关能够正确处理；
- 后向条件分支能够反复跳转；
- 分支条件从“成立”变为“不成立”时，CPU 能够正确退出循环；
- LCD 状态机完成约 1 ms 硬件复位、120 ms 上电等待、初始化命令和全屏清零流程。

调试模式下 LED5 点亮，表示 LCD 控制器内部已经置位 `initialized`。

### 4.4 阶段四：LCD 测试图案

CPU 设置 LCD 的页地址和列地址，然后连续写入 256 个 `0xAA`：

```text
LCD_CMD  <- 0xB0
LCD_CMD  <- 0x10
LCD_CMD  <- 0x00
LCD_DATA <- 0xAA，重复 256 次
```

CPU 的写请求速度远高于 LCD SPI 的实际发送速度，因此每次 MMIO 写入都可能等待 `lcd_tx_ready`。最终图案正确能够说明：

- CPU 与 LCD 之间的总线等待/就绪握手机制至少能够完成长序列传输；
- 外设就绪后，CPU 能继续执行后续循环和最终成功路径；
- LCD 命令和数据选择信号正确；
- SPI 时钟、串行数据、片选、复位和 RS 管脚约束正确；
- ST7571 接收了初始化及显示数据；
- LCD 模块本身至少能够产生可观察显示。

这里写入的是固定测试纹理，不是文字界面。当前程序主要修改第一页，其余区域在初始化时被清零，所以屏幕可能表现为一条灰色或黑白交替的带状图案。由于 256 个数据字节完全相同，仅凭肉眼看到重复纹理不能严格证明每个字节都没有丢失或重复；这一性质仍需结合 RTL 仿真或改用带位置特征的渐变图案验证。

### 4.5 阶段五：最终 PASS

LCD 数据发送完成后，程序依次执行：

1. 向 GPIO 写入 `0xFF`，使 8 个 LED 全亮；
2. 通过 UART 输出 `PASS`；
3. 向 `0xFFFF_FFF0` 写入 `TOHOST=1`；
4. 进入由 `JAL` 构成的无限循环，保持最终状态。

因此，串口出现 `PASS` 表示 CPU 已经按顺序通过前面的 BRAM 检查、LCD 状态等待和 LCD 数据发送。调试模式下 LED7 点亮，则是 `TOHOST=1` 的独立硬件指示。

## 6. UART 输出为何是重要证据

正确显示 `BOOT` 或 `PASS` 并不只是证明“串口能亮”。一个字符从软件到电脑需要经过：

```text
CPU 执行 SW
  -> 地址译码选中 UART_TXDATA
  -> 总线根据 uart_tx_ready 等待
  -> UART 发送器锁存 8 位字符
  -> 按 115200 8N1 串行化
  -> FPGA T4 管脚
  -> 板载 CP2102
  -> USB
  -> Windows COM 端口
  -> 串口终端
```

`BOOT` 和 `PASS` 的字母、顺序与波特率均正确，说明上述整条链路工作正常。如果总线在 UART 忙时没有正确停顿，通常会出现字符丢失或重复；如果时钟频率或波特率分频错误，通常会出现乱码。

当前 UART 只实现 FPGA 向电脑发送。`uart_rxd` 虽然进入了板级同步器，但没有接入 CPU 可读取的接收器，所以在终端键入字符没有响应是预期行为。

## 7. 三条观察通道的一致性

本测试特意使用三种输出，目的是避免单一现象造成误判：

| 通道 | 主要优点 | 主要局限 |
|---|---|---|
| LED | 上电即可观察，不依赖电脑终端 | 信息量少，只能表示阶段或状态位 |
| UART | 能按时间顺序输出明确文本 | 依赖 USB-UART、驱动、COM 口和参数设置 |
| LCD | 验证较复杂的慢速外设与总线等待 | 没有读回反馈，内部完成与物理显示必须结合判断 |

当前实测中，LED 最终全亮、UART 输出 `PASS`、LCD 出现测试图案，并且调试 LED7 表示 `TOHOST=1`。这些结果相互一致，比只看到一个 LED 点亮具有更高的可信度。

## 8. 调试模式各状态位的工程含义

`SW7=1` 时，8 个 LED 不再显示软件写入的 GPIO 数值，而是显示内部状态：

| LED | 内部信号 | 工程含义 |
|---|---|---|
| LED7 | `tohost_latched == 1` | 软件明确执行到成功出口 |
| LED6 | `tohost_latched != 0 && != 1` | 软件明确执行到失败出口 |
| LED5 | `lcd_initialized` | LCD 硬件状态机完成初始化和清屏 |
| LED4 | `uart_busy` | UART 正在发送某一位；脉冲较快，肉眼可能看不清 |
| LED3 | `cpu_reset` | CPU 复位状态；受 SW7 同步过程影响，不适合当作唯一复位证据 |
| LED2 | `clk_locked` | MMCM 已锁定，25 MHz 时钟可用 |
| LED1 | `key_sync[0]` | PB0 已经过双触发器同步后的电平 |
| LED0 | `heartbeat_count[24]` | 25 MHz 板级计数器心跳，约每 0.67 秒翻转 |

测试成功并进入稳定状态后，典型调试值在 `0xA4` 与 `0xA5` 之间变化：LED7、LED5、LED2 常亮，LED0 闪烁。

## 9. 失败路径的含义

如果 `DMEM` 读回值不等于 ALU 计算值，程序会：

- 向 LED 写入 `0x55`，即 LED0、LED2、LED4、LED6 点亮；
- 向 `TOHOST` 写入 `2`；
- 停留在失败循环。

此时调试模式下 LED6 点亮、LED7 熄灭。失败原因可能位于 ALU、流水线相关处理、DMEM、数据总线或分支比较路径，不能仅凭 `0x55` 进一步区分。若需要精确定位，应增加分阶段错误码或使用 ILA 捕获流水线和总线信号。

## 10. 综合与实现结果的含义

按照下板操作文档，XC7A100T/CSG324 版本的参考实现结果为：

| 项目 | 验收要求/参考结果 | 含义 |
|---|---|---|
| WNS | 参考约 `+24.40 ns`，要求大于 0 | 最差建立时间路径仍有正裕量 |
| WHS | 参考约 `+0.104 ns`，要求大于 0 | 最差保持时间路径仍有正裕量 |
| TNS/THS | `0` | 没有累计的建立/保持时间违例 |
| DRC | 0 violations | 没有 Vivado 报告的设计规则错误 |
| Route Status | 0 routing errors | 所有需要连接的网络均完成布线 |
| Block RAM Tile | 约 4 | IMEM 和 DMEM 被实现为片内块 RAM，而不是大量 LUT |

这些报告证明设计在工具的时序模型和规则检查下可以可靠实现，但它们不验证程序语义。反过来，板上出现 `PASS` 证明当前程序路径能运行，却不能代替静态时序分析。两类证据必须同时保留。

根据启动程序和板上现象，本次实板测试覆盖：

- 低有效板级复位及同步释放；

- 基础寄存器读写；

## 12. 本次测试不能证明的内容

即使全部现象符合预期，也不能由本次测试直接推出以下结论：

- 其余未执行指令全部正确，例如 `SUB`、移位、SLT/SLTU、字节访存、`JALR` 等；
- 所有寄存器、DMEM 全部地址及边界访问都正确；
- 异常、非法指令、溢出和复杂中断处理全部正确；
- I-Cache、D-Cache 和动态分支预测在实板上正确，因为当前均被关闭；
- UART 接收正确，因为当前没有实现 RX 功能；
- LCD 全部页面、像素、灰度和命令均正确；
- 外部 SRAM、数码管、VGA、以太网、蓝牙、蜂鸣器和扩展口正确；
- 设计在更高 CPU 频率、不同温度和长时间运行下仍然稳定；
- 断电后能够自动启动，因为当前 bitstream 只通过 JTAG 写入易失配置存储，尚未写入 SPI Flash。

因此，准确的结论应当是“当前 bring-up 程序覆盖的硬件路径通过”，而不是“CPU 所有功能已经完全验证”。完整 CPU 正确性仍需要模块级、指令级和系统级仿真测试支持。

## 13. 测试结论

根据用户确认的实测现象，本次下板测试判定为通过：

1. FPGA 能被正确配置，时钟和复位链路正常；
2. CPU 能从 BRAM 启动并执行预置程序；
3. 基础 ALU、流水线数据相关、DMEM 和分支循环能够协同工作；
4. GPIO、UART、LCD 和 `TOHOST` 的 MMIO 通路正常；
5. UART 文本、LED 状态和 LCD 图案三条观察通道结果一致；
6. 当前硬件平台已具备继续开展完整指令测试、外设交互和 Cache/分支预测实板验证的条件。

本次通过应保存为后续修改的基准版本。以后每次启用一项高级功能，都应重新确认最终 `TOHOST=1`、UART 输出 `PASS`、LED 状态和 LCD 图案保持一致。
