# 验收答辩重点问答与演示清单

## 1. 两门课程边界

**问：两个项目共用一套系统，是否重复计分？**

答：开发板和运行平台共用，但评价对象不同。计组评价 CPU 指令系统、微码、流水控制、附加功能和性能；汇编与接口评价 LCD 协议、控制器 IP、MMIO 驱动、汇编应用和软硬件协同。答辩和报告分别围绕各自对象展开。

## 2. 计组重点问答

### 为什么流水线不是所有程序都更快

同频比较时，短程序会受到流水填充、分支冲刷、load-use 和 Cache 冷启动影响。流水线真正优势来自更短关键路径和更高工作频率。连续计算实验中，流水线虽然多四个周期，但布线后频率从 83.33 MHz 提高到 90.91 MHz，CPU 时间最终缩短约 6.44%。

### 为什么溢出行为和标准 RV32I 不同

标准 RV32I 加减按模二的三十二次方运算。本项目按照课程要求，把 ADD、SUB、ADDI 有符号溢出定义为异常，原因码为 16。答辩时必须明确这是课程扩展。

### 为什么 mepc 保存 PC 加四

当前系统没有完整 CSR 写指令，最小异常处理程序需要直接 MRET 返回。课程化实现因此把 mepc 保存为故障指令的下一地址。它不是完整特权规范实现，报告已明确限制。

### 为什么中断不能立即进入

若更老的 store 或 Cache 缺失尚未完成，立即冲刷会破坏精确状态。控制器先锁存 pending，待旧访存完成并到达安全 EX 边界后再进入中断。

### 为什么 D-Cache 选择写直达、写不分配

课程设计优先保证行为简单、MMIO 副作用明确和验证可控。写直达便于保持下层存储一致，写不分配避免 store miss 带来复杂填充状态。代价是写流量较大。

### 为什么 MMIO 必须旁路 Cache

外设读写具有时序和副作用。若缓存 UART、LCD 或蜂鸣器地址，可能读取旧状态、合并多次写入或延迟副作用。旁路和强顺序能保证一次请求对应一次外设操作。

### 13 组测试与 README 中早期 12 组记录为何不同

当前 sim/run_all_tests.tcl 明确列出十三个 testbench，其中包含后来加入的俄罗斯方块系统测试。答辩以当前脚本和附加功能测试文档的十三组记录为准。

### 下板究竟证明了什么

bring-up 证明 JTAG、时钟、复位、BRAM、基础 CPU 路径、GPIO、UART、LCD 和 TOHOST 能形成闭环。约 56 秒的俄罗斯方块下板视频进一步记录了活动方块下落、固定棋盘累积和画面持续变化，证明 CPU 能在真实 FPGA 上长期执行完整汇编应用，并通过 GPIO 与 LCD MMIO 完成交互。每条指令边界、Cache 替换、中断现场和预测器训练仍由定向仿真与性能计数证明。

### 为什么计组也讲俄罗斯方块

俄罗斯方块在计组答辩中充当 CPU 的综合工作负载。它同时使用分支、算术、加载、存储、循环和 MMIO，能把流水线、BRAM 和外设连接成可观察的整机结果。计组只解释 CPU 如何执行程序和维持总线语义；碰撞、旋转、消行以及 LCD 协议仍由汇编与接口答辩展开，因此不会重复计分。

## 3. 汇编与接口重点问答

### 为什么选择 ST7571 LCD

它需要硬复位、上电等待、初始化命令、四线 SPI 和连续数据发送，能够完整体现接口控制器的状态机、握手和软件驱动设计，比只控制 LED 更能体现课程工作量。

### lcd_spi_master 和 lcd_controller 如何分工

spi_master 只负责一个字节的位级发送，控制 CS、SCK、MOSI 和 RS。lcd_controller 负责复位、初始化、清屏、用户请求调度、棋盘缓冲和刷新流程。两者通过 valid、ready、busy、done 协作。

### 如何保证一次 MMIO 写只发送一次

地址译码器只在 req 与 ready 同时成立时产生接受事件。控制器接受后立即离开 IDLE 并拉低 ready，等待 SPI busy 和 done 完成后才再次接受请求。CPU 在 ready 为零时保持请求和写数据。

### IP 核是否真的可复用

IP 目录只包含 component.xml、两份 RTL 和 XGUI，不依赖本项目 CPU 顶层。端口和时序参数由 component.xml 声明，可以在 IP Catalog 注册并在 Block Design 中例化。正式答辩需用 Catalog、Validate 和输出产品截图闭环证明。

### 为什么棋盘按行存储

俄罗斯方块的碰撞、锁定和消行都以行位图实现最直接。每行十位，满行等于 0x3FF，左右边界和相交检查都能用移位与按位操作完成。

### 旋转遇到边界怎么办

先尝试原位置的下一旋转状态。若碰撞，再分别尝试向左和向右移动一次；仍失败就保持原状态。这是简化的 wall kick。

### 软件和硬件为什么不逐像素分工

软件适合维护棋盘和游戏规则，硬件适合执行重复、时序严格的像素映射和 SPI 发送。软件只上传二十行逻辑数据，硬件负责把每格映射为八列实体和两列间隔，显著减少软件工作量。

### 蜂鸣器为何不阻塞 CPU

软件只写一次 BUZZER_TRIGGER。硬件内部计数器产生约二 kHz、持续约一百二十毫秒的波形，CPU 可以继续执行游戏逻辑。

## 5. 汇编现场演示脚本

建议总时长控制在 4 分钟以内，保留 1 分钟余量。

| 时间 | 动作 | 画面与讲解 |
|---|---|---|
| 0:00–0:20 | 展示开发板并复位 | 说明 FPGA 型号、LCD、手柄和蜂鸣器位置，观察 LCD 初始化 |
| 0:20–0:40 | 拨动 SW0 开始 | 展示新棋盘和首个方块，说明汇编程序进入主循环 |
| 0:40–1:15 | 左右移动 | 分别按左、右键，说明 GPIO 边沿检测和碰撞检查 |
| 1:15–1:45 | 旋转 | 按上键，靠近边界时展示旋转或 wall kick |
| 1:45–2:15 | 软降与锁定 | 按住下键，展示连续下降和锁定到固定棋盘 |
| 2:15–3:20 | 消行 | 使用预先准备的局面完成一行，观察画面压缩和蜂鸣器提示 |
| 3:20–3:45 | 重新开始 | 操作 SW0，展示棋盘与状态清零 |
| 3:45–4:00 | 收尾 | 镜头同时包含 LCD、手柄和开发板，说明演示版本信息 |

## 6. 演示失败时的备用口径

- LCD 无画面：先确认配置灯、MMCM locked 和 lcd_initialized 指示，再检查复位极性和管脚约束。不要直接宣称 CPU 故障。
- UART 乱码：检查 COM 口、115200 波特率、8N1 和二十五 MHz 分频参数。
- 按键无响应：确认使用正确手柄方向键，检查 SW0 状态、按键同步与防抖指示。
- 蜂鸣器不明显：保留仿真中 BUZZER_TRIGGER 与波形证据，同时说明实物音量和音色必须由现场观察确认。
- 现场无法消行：播放同一最终版本录制的短视频，并展示对应固件哈希；不要用不同版本视频替代。
